Project summary

A risk score is not yet a review decision.

This project examined home-equity-line-of-credit risk using interpretable machine-learning methods and a user-facing decision workflow. The objective was not only to classify applicants, but also to help a reviewer understand which factors influenced a prediction and where human judgment should remain in the process.

I evaluated model behavior, used a decision tree to show global structure, applied SHAP to explain feature influence, and built an application view that returns understandable feedback. The repository makes the code and analysis inspectable rather than presenting performance claims without context.

Challenge

Balance predictive value, costly errors, and explanation.

Credit-risk decisions contain asymmetric costs. A model that rejects too broadly can exclude viable applicants and create unnecessary manual work. A model that approves risky applications can create financial losses. Overall accuracy alone cannot describe that tradeoff, and an opaque probability score offers little support to a reviewer or applicant.

The design question was how to connect model selection, class-specific performance, local explanations, and human review into one coherent decision-support concept.

Constraints

A classroom dataset, not a production lending system.

  • Dataset scope: Results reflect the project dataset and evaluation design; they are not claims about production deployment.
  • Fairness and regulation: Explainability does not by itself establish fairness, compliance, or suitability for credit decisions.
  • Threshold choice: The balance between precision, recall, loss, and review volume depends on institutional costs and policy.
  • Human interpretation: Feature influence must not be presented as a causal explanation.
  • Scenario estimates: Savings and review reductions are modeled implications under assumptions, not realized business outcomes.

What I built

Model evidence translated into reviewer context.

I prepared the analysis workflow, compared model behavior, and focused evaluation on the errors that mattered to the decision. The selected approach reached 73% accuracy and 97% precision on the relevant project evaluation, while the decision tree and SHAP views provided complementary explanations: one showed broad decision structure and the other showed how features influenced individual or aggregate predictions.

I then built an interface that moves beyond a binary output. It presents the assessment, relevant factors, and feedback in a form a person can examine. This reframes machine learning as one input into a controlled review process rather than an automated final authority.

Explainability is useful when it improves the next decision, not when it merely decorates a prediction.

Results

Performance with business implications made explicit.

  • 73% accuracy and 97% precision in the documented project evaluation.
  • Decision-tree and SHAP views for global and feature-level interpretation.
  • Scenario analysis estimated up to $73,000 in monthly savings under stated assumptions.
  • The same scenario suggested a potential 27% reduction in manual review.

The financial and workflow figures are analytical estimates, not realized operating results. Their purpose is to connect threshold and review choices to business consequences that stakeholders can question.

Methods

Analytical and product approach.

  • Data preparation and supervised classification.
  • Evaluation using overall and class-specific metrics.
  • Decision-tree visualization for global interpretability.
  • SHAP analysis for feature influence and local explanation.
  • Scenario modeling around manual review and error costs.
  • Application design for reviewer feedback and human oversight.

Reflection

What production readiness would require.

I would add subgroup performance analysis, calibration, stability testing, policy review, data-lineage controls, and a documented model-risk process before considering any operational use. Explanations would also need user testing with actual reviewers to ensure they improve decisions rather than create automation bias.

The main lesson was to connect model evaluation to the workflow around it. A technically strong classifier can still be a weak decision system if its costs, explanations, and escalation path are not designed.
